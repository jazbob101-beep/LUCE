# Tomi GPS and `glgps` Reference

## Scope

This reference consolidates what the preserved Tomi evidence establishes about the GPS software stack, its Linux-facing interfaces, observed runtime, the current custom `ttgpsd` state-provider contract, and the limits of identifying the physical receiver. It is not a GPS hardware teardown or a claim that any historical filesystem or OpenTom source tree exactly matches the current installed device.

Evidence labels used here:

- **ESTABLISHED_TT3** — directly supported by Tomi-specific captured or live evidence.
- **LIVE_OBSERVED** — directly observed in a dated Tomi terminal capture or state capture; each section states the date and provenance boundary.
- **EXACT_BINARY** — static finding tied to the listed hash-identified executable.
- **SOURCE_CORRELATED** — defined by the inspected Austin/type-42 OpenTom source, not proven to be the built or running kernel.
- **PROTOCOL_CORRELATED** — format/output evidence from `glgps` or its downstream log, not proof of receiver silicon.
- **COMPARATIVE_ONLY** — another TomTom device or binary; not transferable as Tomi fact.
- **UNRESOLVED** — the preserved evidence does not decide the question.

## What is known about the physical GPS hardware

**The physical receiver package/chip remains unresolved.** Tomi’s captured `ttgo.bif` contains `GPSFirmwareVersion=2.15.0 65947` (**DEVICE_DIAGNOSTIC / firmware string**). The Austin/type-42 OpenTom profile selects numeric GPS type 130, named `GOGPS_GL_BCM4750` / “Global Locate Barracuda” (**SOURCE_PROFILE**). The Aug. 24 runtime state also reports `receiver_gpstype=130` and “Barracuda” (**LIVE_OBSERVED software label**).

These facts identify software/profile labels and a firmware-version string, not the physical silicon/package. The 2018 GLL 2.16.201 runtime label is generated by GLL and is not a GPS-module firmware response. No direct physical inspection, package marking, board-level tracing, or device diagnostic uniquely identifies the receiver. No TT4 or TJ hardware identity is imported here.

## Linux / platform integration

The Tomi kernel log and profile identify the S3C2412/Austin software platform. In the inspected OpenTom working source, the type-42 profile (`src/linux-s3c24xx/arch/arm/mach-s3c2410/tomtomgo-ioaustin.h`) sets `gpsdev="ttySAC1"`, GPS type 130, `GPS_RESET=GPC5` (inverted), `GPS_ON=GPF4`, `GPS_POWERON_OUT=GPF3`, GPS TX/RX on GPH4/GPH5, and CTS/RTS on GPG9/GPG10. These are **SOURCE_CORRELATED profile definitions**, not live GPIO electrical measurements or proof of the exact kernel image running in the Aug. 24 session. The working OpenTom checkout was dirty; its inspected HEAD was `eb3d2037315bde5da2875b38cba4efba9d47eac7`, and the relevant source files were not established as tracked blobs at that HEAD.

The source driver `src/linux-s3c24xx/drivers/barcelona/gps/gps.c` registers `/dev/gps` with major 243. Its `IOW_GPS_ON` and `IOW_GPS_OFF` ioctl cases explicitly log and ignore those requests; `IOW_GPS_RESET` invokes the source reset helper. The driver also exposes a reset control path and GPS timestamp/PPS-related logic. In the Barracuda profile path, source initializes platform pins/UART and GPS power; the code comments that it normally avoids resetting Barracuda on every start, but source contains a first-start reset branch. This does not establish what occurred in the observed boot. The header `include/barcelona/Barc_gps.h` defines the ioctl names and device major.

No GPS-facing physical MMIO base/address or live GPIO level was validated by the Tomi GPS investigations. GPIO names above are profile-level mappings. Do not import TJ/Atlas III MMIO addresses. The inspected source is correlation only; it is not a frozen exact build input or proof of live kernel correspondence.

## `glgps`

### Startup and runtime model

In the Aug. 24 session, a custom Tomi-side script `/mnt/sdcard/opentom/thomas/gps/start-gps.sh` set `PATH` and `LD_LIBRARY_PATH=/mnt/sdcard/opentom/lib`, linked `/dev/gpsdata` to `/dev/ttySAC1`, created `/var/run/gpspipe`, started a separate `ttgpsd`, then launched `/mnt/sdcard/bin/glgps normal` and a separate `time-sync.sh`. The runtime log says `glgps` read `/mnt/sdcard/gl/cfg/glconfig.xml`, opened `/dev/gpsdata`, found `/proc/barcelona`, and opened `/dev/gps`.

This establishes one **LIVE_OBSERVED custom-run topology**, not the default TomTom navigation launch path or every current boot. The historical extracted `/etc/rc.glgps` instead selects `/mnt/sdcard/bin/glgps` when present (otherwise `/bin/glgps`) and launches `glgps normal` in the preserved image. Its hash is `4ae11ef1c6b64a41d18158c2e05977d7c346831da6f7cc66bc9fef3c834e2a44`. The round-trip package preserves that historical script byte-identically; it does not prove it is installed in the later custom root.

### Device interfaces and data flow

```text
GPS receiver / serial endpoint (physical protocol not captured)
    ↕  S3C UART endpoint reported as /dev/ttySAC1
    ↕  current symlink /dev/gpsdata -> /dev/ttySAC1
glgps normal
    ├─ control/timestamp/platform interface: /dev/gps, /proc/barcelona
    ├─ GLL text output including NMEA sentences and $PGLOR extensions
    ↓  /var/run/gpspipe (named FIFO)
ttgpsd (separate consumer)
    ├─ /var/run/ttgps.state
    ├─ /var/run/ttgps.satellites
    └─ /var/run/ttgps.raw (+ rotated ttgps.raw.1)
```

The Aug. 24 transcript directly observes the symlink, device nodes, process command lines, FIFO and output files. The 2026-09-28 RFNAV-006 characterization re-observed the same active topology on the live device and captured the current startup script and process command lines. It does **not** capture raw bytes at the UART, so the arrows describe the observed software endpoint and downstream flow, not a byte-level proof of every receiver exchange. `/dev/gps` is a TomTom platform control/timestamp device, not the serial stream. `ttgpsd` is a custom separate consumer; no evidence here establishes that stock PNDNavigator consumed these custom output files.

The Aug. 24 capture reports 72,330 valid parsed sentences, with no checksum or malformed-sentence errors before shutdown. Its last ordinary RMC carried UTC date `240826` (2026-08-24) and a valid status. Exact coordinates are intentionally omitted. No raw UART capture, receiver binary-message dump, socket/TCP GPS interface, or independently confirmed baud/protocol negotiation is present. The historical `glconfig.xml` specifies port `/dev/gpsdata`, baud 115200, and `lto.dat`; that is extracted configuration, not proof of the exact live custom-run config contents or receiver-side wire settings.

### Current `ttgpsd` state-provider contract — 2026-09-28

The RFNAV-006 live inspection established the current script-level provider contract more precisely. `/mnt/sdcard/opentom/thomas/gps/start-gps.sh` removes and recreates `/var/run/gpspipe` as a named FIFO, starts `ttgpsd` with that FIFO as input, and writes the current state outputs to:

```text
/var/run/ttgps.state
/var/run/ttgps.satellites
/var/run/ttgps.raw
/var/run/ttgps.raw.1   (rotation observed)
```

`/var/run/gpspipe` and `/var/run/glgpsctrl` were live named pipes. RFNAV and other downstream applications must **not** consume `/var/run/gpspipe` or compete for `/dev/ttySAC1`; doing so could steal or perturb the stream intended for `ttgpsd`. `/var/run/ttgps.state` is the accepted read-only application-facing state source for RFNAV-006.

The state file is schema version 1 and exposes, in one coherent snapshot, provider health/freshness (`sequence`, `state_written_uptime_ms`, `last_sentence_uptime_ms`, `alive`, `stream_open`), fix validity (`navigation_valid`, `position_valid`, `fix_valid`, `fix_quality`, `fix_type`), position (`latitude_deg`, `longitude_deg`), motion (`speed_mps`, `course_true_deg`), dilution (`pdop`, `hdop`, `vdop`), satellite counts, and UTC fields. RFNAV does not need `/var/run/ttgps.satellites` for ordinary movement scoring.

Across both 300-snapshot RFNAV-006 captures, state publication was approximately **1.666 Hz**. For accepted live-fix samples, `state_written_uptime_ms - last_sentence_uptime_ms` never exceeded **1.03 seconds**. A two-second freshness bound is therefore a conservative initial application threshold, not a receiver specification.

The no-fix state remained explicit and machine-readable while the provider stayed alive: the moving capture repeatedly showed `alive=1` and `stream_open=1` with `navigation_valid=0`, `position_valid=0`, `fix_valid=0`, blank latitude and course, and continuing parser/state updates. This lets RFNAV distinguish **provider alive but no fix** from provider failure without reading the FIFO.

### RFNAV-006 source audit and implemented witness policy — 2026-09-29

The local `nxgps-milestone1` provider source was inspected and exercised directly by host tests. `ttgpsd` writes a `.new` file, flushes/fsyncs/closes and renames it; clients must reopen the snapshot. Target publication sequence/counters are 32-bit unsigned long, uptime fields are 64-bit unsigned long long, and the clock is `/proc/uptime`.

`parse_rmc` advances `last_rmc_uptime_ms` even when status or speed is unusable. `motion()` leaves prior mps/motion_valid when knots are blank, and accepts a numeric prefix; `parse_vtg` can replace knots without recomputing mps. GGA/GSA can restore broad validity after an invalid RMC. These are reproduced source-contract findings, not a new hash binding to the installed provider executable.

The isolated RFNAV-006 candidate therefore verifies a checksum-valid active RMC in the snapshot's `last_sentence_raw`, with strict coordinates/knots agreeing with published degrees and rounded mps. Its last-sentence time must equal last-RMC time. The motion key is provider PID/start plus that verified RMC arrival time. A later unrelated publication may retain the witness only when RMC time and relevant fields are unchanged. New unwitnessed RMC, later GGA/GLL coordinate writes or equal/later VTG cause degraded state. Equal timestamps do not count as distinct measurements; same-timestamp batches cannot be separated by schema 1. No provider modification was needed for this conservative implementation.

Publication, sentence, RMC, GGA and GSA freshness is <=2000 ms against target uptime; future/reversed time, restart/EOF/reopen, no-fix, estimated quality and validity gaps pause scoring and break pending transitions/anchors. Only GPS quality 1 and fix type 2/3 qualify. Enter >=0.25 m/s and exit <=0.10 m/s each require three distinct witnessed updates; intermediate speeds cancel pending transitions while retaining established state. A 100 m/s speed sanity limit and geographic displacement policies are provisional application choices. No HDOP or satellite-count threshold is inferred from the walk.

### RFNAV-006 GPS application contract carried forward

The following rules are durable enough to bake into RFNAV-006 production design now:

1. Read `/var/run/ttgps.state`; do not open `/var/run/gpspipe`, `/dev/gpsdata`, or `/dev/ttySAC1` from RFNAV.
2. Treat `alive`/`stream_open` separately from navigation/fix validity. Provider-alive/no-fix is a normal state, not an application failure.
3. Geographic RF scoring pauses when navigation/position/fix validity is false; ordinary RFNAV-005 signal tracking remains usable.
4. Use the provider position as context, but never infer motion from accumulated coordinate displacement alone.
5. Use reported speed as the primary motion gate. Repaired-rig v002 refines the initial implementation policy to enter at >=0.25 m/s and exit at <=0.10 m/s, each after three distinct fresh motion-bearing updates. Repeated publications of one measurement must not advance persistence. Invalid, stale or estimated fixes pause scoring immediately and break pending movement/displacement continuity.
6. Derive Signal-Rose movement bearing from accepted geographic displacement after motion has been established. `course_true_deg` may corroborate movement later, but must not drive direction while stationary or no-fix.
7. Do not use `fix_quality_name=estimated` as directional-scoring evidence in the initial production implementation. It may still be displayed as degraded position context.
8. A state age of two seconds is a conservative initial stale threshold based on the observed ~1.66 Hz provider and <=1.05 s write-to-last-sentence lag across the characterized captures; this is an application policy, not a receiver guarantee.
9. Do not hard-code a satellite-count or HDOP cutoff from these captures alone. Retain those fields for confidence/diagnostic use; v002 completes the deferred clean moving characterization without establishing a stricter quality gate.

These rules close the state-provider architecture question and the stationary false-motion question. They do **not** constitute full RFNAV-006 field qualification.

### Shutdown behavior from the later binary

For the 2018 specimen only, static analysis establishes that `glgps` formatted `$PGLOR,FIN,1*36` itself. FIN reason 1 maps to `ASIC is DEAD`; ordinary control-FIFO quit maps to FIN 0. The observed transcript records the final FIN 1 at uptime 7,393,220 ms, about 360 ms after the last normal batch, while `ttgpsd` survived with the stream open and no EOF/reopen or parser errors. The 2018 binary’s ASIC-dead path uses one-shot ASIC-init/MEIF transaction watchdogs (normally 1500 internal engine ticks, plus a separate 75-tick early-init path); the tick-to-time conversion and the specific expired site are unknown.

The custom `time-sync.sh` log showed nine successful GPS-to-system-to-RTC sync entries in the same second as shutdown. This is a temporal precursor, not proof of causation. The evidence attributes the termination mechanism to `glgps`’s internal ASIC-dead classification; the lower-level trigger remains unknown. The kernel source’s ignored `IOW_GPS_OFF` behavior means that final ioctl/log is cleanup, not proof that Linux powered the physical receiver off. No direct USB/PPP/UART-driver cause was established.

## GPS protocol and firmware findings

**PROTOCOL_CORRELATED:** captured downstream text contains standard NMEA-style GGA/GSA/GSV/RMC sentences and GLL-generated `$PGLOR` extensions such as RID and FIN. `$PGLOR` is produced by the TomTom/Broadcom GLL process, not established as receiver-originated UART text. The raw serial wire protocol remains **UNRESOLVED**: no raw UART bytes, SiRF binary messages, receiver message IDs, command/response sequence, checksum, or firmware-query exchange were captured. A GLL software label or Barracuda profile cannot identify the physical chipset.

- Historical 1,090,108-byte executable: GLL 2.15.0 build 65947 (2009) (**EXACT_BINARY**).
- Aug. 24 live GLL RID: `2.16.201` (**LIVE_OBSERVED GLL software identity**, not GPS firmware identity).

## Reset / power / lifecycle

The Austin profile and `gps.c` source establish a platform-controlled reset/power design, but no live electrical level, reset pulse, antenna/LNA state, or measured time-to-fix is established. The 2009 binary-specific epoch work used a historical test in which setting Linux time before start and a cold-start job still produced a 2007 date; that conclusion belongs to that run and that hash-identified executable only.

The Aug. 24 run is materially different: it reports GLL 2.16.201 and a valid current 2026 RMC date. The captured run does not isolate whether the difference arose from GLL build, configuration, time-sync behavior, receiver state, or another variable. The 2018 specimen contains RTC provider-related strings, but string presence does not prove provider execution. No controlled, hash-bound comparison resolves the cause of the differing dates.
